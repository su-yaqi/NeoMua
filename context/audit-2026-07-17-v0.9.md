## 结论

v0.9 已实现 Runtime Node 一对多 Runtime Instance、引擎适配器、稳定模型身份与 Runtime Model Binding、Agent 模型偏好、Activation precheck、Conversation/Workflow 模型模式及 Task 冻结等主体结构。

当前实现仍存在两个 P0 信任与安全边界缺陷，以及多个 P1/P2 一致性问题。自动化测试全部通过，但测试没有覆盖实际运行证据与控制面快照不一致、安全策略未应用、连接/验证证据过期等负向场景。因此 v0.9 不能标记为已完成，也不应在未整改或未明确接受风险的情况下合并到主分支。

## 发布阻断项

### P0-1 Node 模型证据不是本地实际证据

- `node_runtime/node_runtime/tasks.py:437-449` 直接从任务 `snapshot` 复制 Runtime、engine、Adapter、model route 和摘要字段，作为 `model_evidence` 上报。
- `backend/app/api/routes/node_socket.py:1872-1895` 将上报证据与控制面从同一任务快照构造的 expected 字典比较。
- 该闭环只能证明消息被回显，不能证明节点实际使用了冻结的 Adapter、配置和模型路由；错误或过期的本地环境仍可能获得 Model Gateway token。

整改门禁：Runtime 必须从本地已应用配置、实际 Adapter 版本、实际模型路由和能力缓存构造证据；控制面持久化并核对后才能签发模型调用凭据。必须增加本地证据与快照不一致时拒绝首次模型调用的测试。

### P0-2 Runtime 安全上限没有完整落地

- `runtime_worker/runtime_worker/worker.py:118-151` 和 `node_runtime/node_runtime/connection.py:245-265` 主要校验引擎、可执行文件与空参数后就报告配置 applied。
- 服务端仅对 permission mode、Tool 和工作目录根做了部分检查；环境变量白名单、网络策略、CPU/内存/并发资源限制、Runtime 最大超时、per-tool approval 等没有形成统一确定性交集和执行器约束。
- 因此配置状态可以显示 applied，但实际进程仍可能在更宽的环境和资源范围内运行。

整改门禁：定义有类型、可验证的安全策略 Schema；Activation 和 Task 创建计算确定性交集；平台与节点执行器在进程边界应用环境、目录、网络、超时和资源限制；无法执行的策略必须阻断并上报结构化错误。

## P1 高优先级缺陷

### P1-1 Node 离线未使所属 Runtime Instance 不可用

- `backend/app/api/routes/node_socket.py:2697-2705` 断线只清理 Node `connection_id`。
- `backend/app/runtime/catalog.py:93-106` 的 Runtime ready 检查不验证 Node 在线状态或能力报告时效。

结果：离线 Runtime 仍可能出现在目录并通过 Activation precheck，直到任务调度才失败。

### P1-2 模型 Binding 不随依赖和能力变化失效

- `backend/app/runtime/catalog.py:54-89` 只按持久化 `AVAILABLE` 状态构建模型目录。
- 目录和 Activation precheck 没有把当前 capability fingerprint、Provider Config 状态、验证时间和路由依赖纳入可用性判定。

结果：Provider 停用、Adapter/能力变化或验证过期后，旧 Binding 仍可能被展示和预检接受。

### P1-3 迁移猜测稳定模型身份

- `backend/app/alembic/versions/f9b2c4d6e810_add_v0_9_runtime_model_execution.py:506-539` 将所有旧 `provider_slug + model_id` 无条件转换为启用的稳定模型定义。
- 未知供应商、非官方 ID 或歧义数据没有预检和 Admin 确认步骤。

这与 PRD 的“未知/歧义必须阻断，不猜测”冲突。

### P1-4 直接任务可覆盖冻结 Agent Release 的系统提示词

- `backend/app/api/routes/agent_tasks.py:342` 在绑定 Release 时仍优先使用请求 `system_prompt`。

结果：实际执行行为可能与 `resolved_spec_digest` 不一致，调用方能够绕过已发布 Agent 的冻结提示词。

## P2 功能与稳健性缺口

- `conversation_agent` 对 `(conversation_id, agent_id)` 的唯一约束禁止同一 Release 作为多个独立角色出现。
- PRD 要求的 `GET /agent-releases/{release_id}/compatibility` 未实现。
- `agent_task_model_usage` 只有任务级准备/证明记录，缺少按调用序列上报 binding、token/用量、状态和脱敏错误的 `task_model_usage` 链路。
- Runtime 配置 revision CAS 和模型 validation attempt 编号存在并发竞争窗口；冲突可能成为数据库异常/500，而不是确定性 409。

## 主干合并门禁

正常合并至少要求：

1. 关闭两个 P0，并补充能证明本地执行事实和安全上限实际生效的负向测试。
2. 关闭 P1-1 至 P1-4，或由项目负责人逐项明确接受风险、范围与后续修复版本。
3. 更新本审计、`context/project.md` 和 `context/changelogs/v0.9.md` 的状态；不得在风险未关闭时写为“已完成”。
4. 重新执行 Backend、Runtime Worker、Node Runtime、Playwright、前端构建、Ruff、Alembic upgrade/check 和差异检查。

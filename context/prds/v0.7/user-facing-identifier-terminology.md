# 用户可理解的唯一标识术语

## 1. 目标声明

### 背景

项目、Agent、Skill、MCP、Plugin 与 Spec 标准页面直接向用户展示英文技术术语 `Slug`。该字段虽然承担稳定路由与系统引用职责，但多数用户无法从名称理解其用途、格式和不可修改性。

### 目标

- 所有业务页面不再把 `Slug` 作为用户字段名称。
- 根据对象使用“项目标识”“Agent 标识”“Skill 标识”“MCP 标识”“Plugin 标识”“标准标识”。
- 通用辅助说明明确该值用于链接和系统引用、创建后不可修改，并说明字符约束。
- 列表、详情、错误信息和 Runtime 引用位置使用相同术语。

### 不在范围内

- 重命名数据库字段、API 参数、TypeScript/Python 内部变量或 Manifest 键。
- 修改标识格式、唯一性范围、创建后不可修改规则或现有值。
- 自动根据名称生成标识。

## 2. 模块影响

| 模块 | 影响类型 | 说明 |
|------|---------|------|
| `agent_management` | 修改 | Agent、Skill、MCP 与 Plugin 的用户可见字段和列表统一使用对象化标识名称 |
| `project_management` | 修改 | 项目与 Spec 标准使用“项目标识/标准标识” |
| `runtime_management` | 修改 | Agent/MCP Runtime 状态不再裸露 `agent_slug`、`server_slug` 技术概念 |

## 3. 功能描述

正常流程：

1. 用户进入创建、列表或详情页面。
2. 页面以当前对象对应的“标识”名称展示字段和值。
3. 创建表单在字段下说明用途、格式与不可修改性。
4. 后端仍按原 `slug` 字段接收和返回数据。

边界条件：内部日志、OpenAPI、代码变量和 URL 参数继续保留 `slug`；供应商选择中的 `provider_slug` 不作为文本输入展示，因此不调整。

异常处理：后端返回包含 `slug` 的技术错误时，前端创建流程转换为“唯一标识已存在/格式不正确”等业务提示，不改写未知错误。

## 4. 数据变更

无。

## 5. UI 页面

| 变更类型 | 页面 | 路由 | 说明 |
|------|------|------|------|
| 修改 | 项目与 Spec | `/projects`、`/system/spec-standards` | 使用项目标识和标准标识 |
| 修改 | Agent 能力管理 | `/system/agents`、`/system/skills`、`/system/mcp-servers`、`/system/plugins` | 创建、列表和详情使用对象化标识 |
| 修改 | Runtime 状态 | `/system/runtimes`、节点详情 | 使用“Agent 标识/MCP 标识”说明技术引用 |

## 6. 验收标准

- [ ] 业务页面不再出现未解释的 `Slug` 字段名称。
- [ ] 标识输入说明用途、字符限制和创建后不可修改性。
- [ ] 列表与 Runtime 引用能区分展示名称和唯一标识。
- [ ] API、数据库、Manifest 和既有标识值没有变化。
